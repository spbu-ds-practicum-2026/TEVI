# Техническое решение проекта «Middleware»

## Введение
- **Бизнес-задача:**
	Целевой сервис (API-шлюз) принимает поток запросов от пользователей. При резком скачке трафика - например, из-за всплеска активности или DDoS-атаки - одиночный сервер не справляется с нагрузкой: растет задержка ответа, вплоть до отказа обслуживания.
	Для защиты сервиса перед ним ставится слой фильтрации трафика (rate limiting middleware), ограничивающий число запросов от каждого пользователя за единицу времени. На одном узле этот слой сам становится узким местом (bottleneck) и единой точкой отказа (single point of failure): при его отказе весь трафик уходит на сервис без ограничений, либо сервис становится недоступен.

- **Идея решения:**
	Создать распределенный слой фильтрации (middleware), состоящий из нескольких независимых узлов, каждый из которых принимает запросы и локально ведет счетчик запросов по пользователям. Система не использует единый централизованный кэш, чтобы исключить единую точку отказа (SPOF). Узлы обмениваются состоянием для совместного контроля глобального лимита пользователя, обеспечивая высокую доступность (AP-модель) и сохраняя работоспособность при сетевых разделениях.

- **Краткое описание:**
	Distributed rate limiting middleware - учебный проект, реализующий прототип промежуточного слоя фильтрации запросов, который стоит перед целевым сервисом, ограничивает трафик и сохраняет работоспособность системы при отказе части узлов.

	Проект является распределённой системой, потому что:
	- состоит из нескольких независимых узлов, каждый со своей локальной памятью
	- узлы не имеют общей памяти и общаются сообщениями
	- состояние лимитов согласуется между узлами асинхронно
	- система сохраняет работоспособность при отказе отдельных узлов

- **Цель проекта:**  
	Реализовать прототип распределённого middleware, который:
	- ограничивает число запросов от каждого пользователя за единицу времени
	- сохраняет доступность при отказе отдельных узлов и сетевых разделениях
	- обеспечивает сходимость состояния лимитов между узлами за конечное время

- **Задачи:**
	- спроектировать архитектуру распределённого middleware
	- реализовать приём и обработку входящего трафика на узле middleware
	- реализовать локальный учёт запросов по пользователям
	- реализовать обмен состоянием между узлами
	- реализовать детектор отказа узлов (failure detector)
	- реализовать обработку сетевых разделений и восстановление после слияния
	- реализовать тестирование и chaos-сценарии

- **Основания для разработки:**  
	учебный проект по курсу «Основы распределённых вычислений» в СПбГУ.

## Функциональные требования
Система должна предоставлять следующие функции:
- Приём запросов от пользователей.
- Ограничение числа запросов от одного пользователя в рамках скользящего окна времени.
- Пропуск запроса к целевому сервису с ответом `200 OK`, если лимит не превышен.
- Отклонение запроса с ответом `429 Too Many Requests`, если лимит превышен.

### Ограничения на предметную область
- Система развёртывается на одной машине через `docker compose`.
- Целевой сервис — заглушка, возвращающая `200 OK`.
- Аутентификация не реализуется: обычные запросы идентифицируются по `user_id`, административные — по `admin_id`.
- Система ограничивает по `user_id`, а не защищает от DDoS.
- Размер скользящего окна T и глобальный лимит запросов N являются настраиваемыми параметрами системы и не зафиксированы жестко в коде. Прототип допускает изменение этих значений в процессе работы без остановки кластера.

## Нефункциональные требования
- Гарантия лимита и модель согласованности (AP): Система стремится соблюдать глобальный лимит N для каждого user_id суммарно по всем узлам кластера. В архитектуре отсутствует централизованный кэш для исключения единой точки отказа (SPOF). 
  Величина возможного превышения лимита ограничена:
	- В штатном режиме (сеть целостна) — задержкой распространения состояния между узлами: пока узел не получил обновлённые счётчики от других узлов, он может пропустить часть запросов пользователя, считая, что лимит ещё не исчерпан;
	- При сетевом разделении кластера на k изолированных групп — значением k × N (по N на каждую группу).
	При разделении каждая группа продолжает независимо принимать трафик (AP-выбор). Динамический перерасчёт лимитов между узлами не выполняется. Объединение счётчиков и строгий контроль возобновляются после восстановления связи через обмен состояниями между узлами.
- Масштабируемость: Пропускная способность растёт при добавлении узлов кластера без изменения кода и конфигурации остальных узлов.
- Поведение при сетевых аномалиях (AP-система): При сетевых разделениях доступность ставится выше строгой согласованности. Каждая изолированная группа узлов продолжает независимо принимать трафик.
- Конечная согласованность: При восстановленной связи, продолжающейся доставке сообщений и отсутствии новых запросов счётчики узлов по каждому `user_id` сходятся за конечное время. При сдвиге скользящего окна запросы, вышедшие за пределы последних $T$ секунд, исключаются из подсчёта.
- Отказоустойчивость: При отказе отдельного узла остальные узлы продолжают обрабатывать запросы. Ранее синхронизированные данные сохраняются; несинхронизированные могут быть потеряны.
- Надёжность обмена: Доставка сообщений At-least-once. Слияние счётчиков идемпотентно — повторная доставка не приводит к двойному учёту запросов.
- Обнаружение отказов и восстановление: Система обнаруживает недоступность узла и исключает его из обмена состоянием. Вернувшийся в кластер узел автоматически синхронизирует счётчики без участия оператора.

## Пользовательские сценарии
**Правила работы лимита:**
Ограничение действует для конкретного `user_id` суммарно по всем узлам кластера на протяжении скользящего временного окна длительностью $T$.

Отклонённые системой запросы (получившие ответ `429`) не учитываются в счётчике и не расходуют лимит. Такое поведение выбрано потому, что главная цель middleware — ограничить реальную нагрузку на целевой сервис, а не наказывать пользователя за повторные попытки.

### Отправка запроса в пределах лимита
1. Пользователь отправляет запрос через любой узел middleware.
2. Узел проверяет сумму запросов пользователя за окно.
3. Если лимит не превышен, запрос пропускается к сервису.
4. Пользователь получает ответ сервиса со статусом `200 OK`.

### Превышение лимита запросов
1. Пользователь отправляет $N+1$-й запрос за окно.
2. Узел определяет, что лимит исчерпан.
3. Запрос отклоняется.
4. Пользователь получает `429 Too Many Requests`.

### Восстановление лимита
1. Пользователь ждёт, пока часть запросов выйдет за границу окна.
2. Сумма запросов за окно становится меньше $N$.
3. Следующий запрос пропускается к сервису.
4. Пользователь получает `200 OK`.

### Сетевое разделение и восстановление
1. Установлен глобальный лимит N запросов на окно T.
2. Из-за сетевого разделения узлы теряют связь и разделяются на изолированные группы. Узел А пропускает X запросов, узел Б пропускает Y запросов, при этом локально каждый узел считает, что лимит не превышен (X < N, Y < N).
3. При условии X + Y > N суммарно кластер пропускает запросов больше N - это допустимое поведение для доступной системы при разделении.
4. Связь восстанавливается, узлы синхронизируют счётчики через обмен состояниями.
5. Оба узла учитывают объединённое количество запросов X + Y за окно. Так как X + Y > N, следующие запросы отклоняются со статусом 429 Too Many Requests.
6. После того как старые запросы выйдут за границу скользящего окна T, сумма запросов станет меньше N, и лимит восстановится.

## Административные сценарии

### Администратор меняет общий лимит (кластер целостен)  
1. Администратор отправляет на доступный узел middleware запрос с `admin_id` и новым значением $N$ или $T$.
2. Узел проверяет значение (целое, $> 0$). Иначе возвращает `400 Bad Request`.  
3. Узел применяет новое значение локально и присваивает ему новую версию - номер, больше предыдущего значения версии.  
4. Узел передаёт новое значение остальным узлам кластера.   
5. Каждый узел применяет значение, только если его версия выше текущей. Повторная доставка с той же или меньшей версией игнорируется.
6. Все узлы работают с новым $T$, $N$. Пользовательские запросы обрабатываются без перерыва, перезапуск не нужен.  
### Администратор меняет общий лимит во время сетевого разделения  
1. Администратор отправляет запрос с `admin_id` на изменение $N$ и $T$.  
2. Запрос направляется на доступный узел одной из изолированных групп.  
3. Узел проверяет значение (целое, > 0). Иначе возвращает `400 Bad Request`. При корректном значении применяет его локально и присваивает новую версию — номер, больший предыдущего.
4. Новое значение распространяется внутри этой группы.  
5. Остальные группы продолжают работать со старым лимитом (допущение AP).  
6. Связь восстанавливается, узлы снова обмениваются состоянием. 
7. Все узлы сходятся к одному значению лимита без вмешательства администратора.

## Архитектура системы

**Узел middleware** — самостоятельный экземпляр промежуточного слоя. Обрабатывает запросы пользователей и администраторов, хранит локальное состояние счётчиков, участвует в обмене состоянием с другими узлами. Узлов несколько, они равноправны.

**Rate Limiter** — компонент узла, отвечающий за проверку и учёт запросов по `user_id`. Обращается к хранилищу счётчиков, принимает решение о пропуске или отклонении запроса.

**Хранилище счётчиков** — компонент узла, хранящий счётчики запросов по каждому `user_id` в виде кольцевого буфера временных бакетов. Для каждого бакета хранится вклад каждого узла кластера (G-Counter). Хранилище локальное, in-memory.

**Хранилище конфигурации** — компонент узла, хранящий текущие значения лимита N, окна T и их версию. Обновляется при административных запросах и при получении более новой версии через gossip.

**Сетевой слой** — компонент узла, отвечающий за отправку и приём сообщений между узлами кластера. Обеспечивает передачу данных по сети, сериализацию и десериализацию сообщений, обработку тайм-аутов и сетевых ошибок.

**Gossip** — компонент узла, определяющий логику обмена информацией с другими участниками кластера. Выбирает узлы для обмена, запускает периодическую синхронизацию и передаёт полученное состояние счётчиков в логику слияния.

**Таблица участников кластера** — компонент узла, хранящий идентификаторы и сетевые адреса известных узлов. Используется Gossip для выбора участников обмена, а сетевым слоем — для определения адресатов сообщений. При первоначальном подключении используются адреса заранее известных узлов.

**Детектор сбоев** — фоновый процесс узла, отвечающий за обнаружение упавших и недоступных участников кластера. Периодически выполняет прямые проверки доступности (Ping) случайных участников, а при тайм-ауте — косвенные проверки (Ping-Req) через других соседей. По результатам проверок присваивает и изменяет статусы узлов, обрабатывает опровержения собственного ложного статуса, распространяет изменения статусов по кластеру через gossip.

**Таблица состояний узлов** — локальный in-memory компонент узла, хранящий для каждого известного `node_id`: статус доступности (Alive — доступен, Suspect — подозрение на падение, Dead — считается упавшим), время последнего подтверждения жизни и номер инкарнации. Номер инкарнации — монотонно возрастающий счётчик перезапусков узла, позволяющий отличить перезапустившийся узел от упавшего и опровергать ложные статусы. Используется детектором сбоев для проверок и gossip-слоем для выбора целей обмена.

**Сервер** - это целевой сервис, получающий запросы от узлов middleware и отправляющий в ответ на них `200 OK`

**Распределитель нагрузки** - это сервис, выполняющий разделение нагрузки между узлами и проверяющий их работоспособность

**Список узлов** - это список, находящийся внутри распределителя, который содержит названия всех узлов и данные для отправки к ним запросов

**Список живых узлов** - это список, содержащий только те узлы, которые помечены как "живые" системой проверки работоспособности узлов

**Максимальное число попыток переотправки** - это предварительно заданный параметр распределителя, выражающий число повторных попыток отправки запроса, которые распределитель предпримет в случае, если узел не ответит до таймаута

**Система проверки работоспособности узлов** - это функция распределителя нагрузки, отправляющая запрос к системе health-check подозрительного узла по требованию от самого распределителя. 

**Сценарий нагрузки** - это последовательность действий, которые выполняются с целью имитации нагрузки на тестируемую систему

**Ожидания сценария** - это ожидаемая реакция системы на определённый сценарий нагрузки. В данном случае проверяется число полученных запросов 200 и 429

**Генератор** - это отдельный от системы сервис, выполняющий генерацию запросов к рассматриваемой системе по предварительно заданным сценариям нагрузки

## Технические сценарии

### Сценарий 1. Обработка запроса пользователя (в пределах лимита)
1. Rate Limiter получает `user_id`.
2. Rate Limiter обращается к Хранилищу счётчиков.
3. Хранилище выполняет сдвиг окна: обнуляет бакеты, вышедшие за пределы T, возвращает текущее состояние.
4. Rate Limiter суммирует счётчики по всем бакетам и всем узлам кластера. Значение меньше N.
5. Rate Limiter инкрементирует ячейку своего узла в текущем бакете.
6. Возвращает решение: запрос пропущен.

### Сценарий 2. Превышение лимита
1. Rate Limiter получает `user_id`.
2. Обращается к Хранилищу счётчиков, получает состояние.
3. Сумма счётчиков по всем бакетам и узлам ≥ N.
4. Rate Limiter возвращает решение: `429 Too Many Requests`. Счётчик **не инкрементируется**.

### Сценарий 3. Слияние состояния при получении gossip-сообщения
1. Узел принимает сообщение от другого узла и передаёт его в логику слияния.
2. Логика слияния выполняет сдвиг окна по времени отправителя.
3. Для каждой ячейки `(user_id, bucket, node_id)` берёт максимум из своего и полученного значения.
4. Состояние хранилища обновлено.
5. Слияние идемпотентно: повторное применение одного и того же состояния не изменяет результат, так как `max(x, x) = x`. Устаревшие и повторные сообщения не приводят к двойному учёту.

### Сценарий 4. Восстановление узла после отказа
1. Узел перезапускается, локальное хранилище счётчиков пусто.
2. Узел инициирует запрос состояния у соседей.
3. Узел получает состояния от соседей и передаёт в логику слияния.
4. Логика слияния выполняет merge: для каждой ячейки берёт максимум. Через 1–2 раунда состояние актуально.
5. Rate Limiter готов принимать запросы.

### Сценарий 5. Поведение при сетевом разделении
1. Сеть между узлами нарушена.
2. Rate Limiter продолжает работать по локальным счётчикам. Никаких блокировок нет.
3. Суммарное превышение лимита по кластеру может достигнуть k × N — допустимое поведение AP-системы.

### Сценарий 6. Слияние после восстановления сети
1. Связь восстановлена. Узел получает состояния других узлов.
2. Логика слияния выполняет merge по `max` для каждой ячейки.
3. Сумма счётчиков становится одинаковой на всех узлах.
4. Если сумма ≥ N — Rate Limiter отклоняет следующие запросы с `429`.
5. Через T секунд «лишние» бакеты выходят за окно, лимит восстанавливается.

### Сценарий 7. Разрешение конфликта конфигурации
1. Логика конфигурации получает новое значение N или T с версией.
2. Если версия больше текущей — применяет.
3. Если версия равна, но значения разные — применяет значение узла с большим `node_id`.
4. Одно из конкурентных изменений при разделении теряется — следствие AP-выбора.

### Сценарий 8. Сборка мусора в хранилище счётчиков
1. Фоновый процесс узла запускается с периодом (например, раз в 60 секунд).
2. Для каждого `user_id` проверяется время последнего обращения.
3. Если все бакеты пусты и с последнего запроса прошло больше T — запись удаляется.

### Сценарий 9. Запуск узла middleware
1. Узел запускается в Docker-контейнере.
2. Инициализирует Rate Limiter, хранилище счётчиков, хранилище конфигурации, сетевой слой, Gossip и таблицу участников.
3. Запускает сетевой сервер на заданном адресе и порту.
4. Если узел настроен как первый участник кластера, он начинает работу самостоятельно. Иначе переходит к подключению к существующему кластеру.

### Сценарий 10. Подключение узла к кластеру
1. Новый узел получает адрес хотя бы одного известного участника из конфигурации запуска.
2. Через сетевой слой отправляет известному узлу сообщение о присоединении, содержащее свой `node_id` и сетевой адрес.
3. Получивший сообщение узел регистрирует нового участника и передаёт ему сведения об известных участниках кластера.
4. Новый узел сохраняет полученные адреса в таблице участников.
5. Gossip начинает периодический обмен состояниями счётчиков.

### Сценарий 11. Периодический обмен состоянием через Gossip
1. По заданному интервалу Gossip выбирает участников для обмена, используя таблицу участников.
2. Получает из хранилища полное текущее состояние счётчиков: всех пользователей и актуальные бакеты.
3. Передаёт состояние сетевому слою для отправки выбранным узлам.
4. Сетевой слой получателя принимает сообщение и передаёт Gossip.
5. Gossip передаёт полученное состояние в хранилище для слияния.
6. При последующих обменах объединённое состояние может распространяться дальше.

### Сценарий 12. Обнаружение недоступного узла
1. Gossip периодически инициирует проверку доступности известных участников через сетевой слой.
2. Если ответ не получен в течение заданного тайм-аута, узел помечается как подозрительный.
3. При дальнейших неудачных проверках узел может быть помечен как недоступный.
4. Gossip продолжает обмен с доступными участниками.

### Сценарий 13. Повторное подключение после восстановления связи
1. Сетевой слой снова устанавливает связь с ранее недоступным узлом.
2. Gossip возобновляет обмен сообщениями с этим участником.
3. Получает его полное текущее состояние счётчиков.
4. Передаёт состояние в хранилище для слияния по правилу `max` для каждой ячейки `(user_id, bucket, node_id)`.
5. Продолжает периодический обмен состояниями.

### Сценарий 14. Обновление списка участников
1. Gossip получает информацию о новом участнике через сообщение от известного узла.
2. Проверяет наличие его `node_id` в таблице участников.
3. Если участник новый, добавляет его идентификатор и сетевой адрес.
4. Использует обновлённый список при последующих обменах.
5. Если адрес участника изменился, обновляет запись при получении достоверной информации.

### Сценарий 15. Прямая проверка доступности (Ping)
1. Детектор сбоев по таймеру выбирает случайный узел со статусом Alive из таблицы состояний узлов.
2. Отправляет ему сообщение Ping через сетевой слой и запускает таймер ожидания ответа.
3. При получении Ack обновляет время последнего подтверждения жизни узла; статус остаётся Alive.
4. Если ответ не получен за тайм-аут, узел не считается упавшим сразу: детектор инициирует косвенную проверку (сценарий 16).

### Сценарий 16. Косвенная проверка (Ping-Req) и статус Suspect
1. Детектор выбирает k случайных соседей, которые также знают проверяемый узел.
2. Отправляет им запрос Ping-Req: выполнить Ping целевого узла и вернуть результат.
3. Если хотя бы один сосед вернул Ack от целевого узла, узел остаётся Alive: проблема была в прямом канале, а не в узле.
4. Если результат не получен ни от одного соседа за тайм-аут, детектор устанавливает узлу статус Suspect и распространяет слух через gossip.

### Сценарий 17. Опровержение ложного статуса (Refutation)
1. Узел получает через gossip слух о том, что он сам помечен как Suspect.
2. Узел фактически работоспособен: его детектор увеличивает собственный номер инкарнации на 1.
3. Узел распространяет через gossip слух «Alive с новым номером инкарнации».
4. Узлы, получившие слух, сравнивают номера инкарнаций: новый номер больше хранящегося — статус узла откатывается к Alive. Ложное срабатывание устранено, узел не исключается из кластера.

### Сценарий 18. Переход в статус Dead и исключение из обмена
1. Узел остаётся в статусе Suspect в течение тайм-аута подозрения и не присылает опровержения.
2. Детектор изменяет его статус на Dead и распространяет слух через gossip.
3. Остальные узлы по слуху также помечают узел как Dead в своих таблицах состояний.
4. Gossip исключает Dead-узел из целей обмена; при этом вклад упавшего узла в счётчики не удаляется и продолжает учитываться, пока не выйдет за пределы скользящего окна.

### Сценарий 19. Перезапуск узла и распознавание детектором
1. Упавший узел перезапускается: локальное состояние пусто, номер инкарнации генерируется заново и больше предыдущего.
2. Узел начинает рассылать gossip-сообщения с новым номером инкарнации (механизм подключения к кластеру описан в сценарии 10).
3. Детектор сбоев других узлов получает gossip-сообщение от узла, который ранее был помечен как Dead.
4. Детектор сравнивает номер инкарнации: новый номер больше хранящегося — это означает перезапуск узла, а не возврат старого.
5. Детектор изменяет статус узла с Dead на Alive в таблице состояний узлов.
6. Детектор включает узел в список целей для прямых проверок (Ping) и возобновляет мониторинг его доступности.

### Сценарий 20. Поведение при сетевом разделении и схождение представлений
1. Кластер разделяется на изолированные группы; узлы не получают ответов от узлов другой группы, включая косвенные проверки.
2. Каждая группа независимо помечает узла другой группы как Suspect, затем Dead; обработка трафика и учёт счётчиков продолжаются локально (AP-система, без блокировок).
3. Статус Dead является локальным представлением группы, а не глобальным решением: ни одна группа не прекращает работу.
4. После восстановления связности узлы обмениваются слухами Alive с текущими номерами инкарнаций (перезапусков не было — номера не изменились), взаимно возвращают статусы Alive и возобновляют обмен и слияние счётчиков.

### Сценарий 21. Обработка запроса пользователя на сервере
1. Сервер получает HTTP-запрос
2. Сервер возвращает ответ на него в виде `200 OK` с пустым телом

### Сценарий 22. Запуск сценария нагрузки
1. Оператор запускает генератор через CLI с указанием параметров сценария
2. Генератор асинхронно генерирует и отправляет запросы в систему
3. Генератор собирает статусы ответов и задержки для каждого запроса и записывает их в файл
4. Генератор возвращает 0, в случае если сценарий пройден без критических ошибок (в частности, 500, 503) и если фактические результаты совпадают с ожиданиями сценария, или 1, если нет,

### Сценарий 22.1. Получение запроса и отправка его на узел
1. Распределитель получает запрос от пользователя
2. Распределитель получает живой узел по принципу:
	- Заблокировать изменение списка живых узлов и получение живого узла
	- Если список живых узлов пуст - вернуть ошибку `503 Service unavaliable`
	- Получить узел из списка живых узлов по индексу: счётчик % длина(список живых узлов) (деление с остатком)
	- Прибавить к счётчику единицу
	- Разблокировать изменение списка живых узлов и получение живого узла
3. Распределитель отправляет запрос выбранному узлу

### Сценарий 22.2. Таймаут для ответа от узла
1. Распределитель не получает ответ от узла за время таймаута
2. Распределитель параллельно инициирует принудительную проверку узла системой проверки работоспособности узлов
3. Распределитель проверяет, имеются ли другие узлы в списке. Если нет, то возвращает ошибку `503 Internal server error`
4. Распределитель выбирает следующий, отличный от упавшего, живой узел по принципу из сценария 1.1 и отправляет запрос на него
5. Распределитель повторяет шаги 1-3, пока не получит ответ на запрос к узлу или не достигнет максимального числа попыток переотправки. Внутри каждой попытки также может вызываться принудительная проверка работоспособности
6. В случае достижения максимального числа попыток переотправки, распределитель возвращает пользователю `503 Service unavaliable`

### Сценарий 22.3. Исключение узла из списка на распределение в случае его падения
1. Распределитель получает ответ от системы проверки работоспособности узлов о том, что узел упал.
2. Распределитель исключает его из списка живых узлов

### Сценарий 22.4. Получение результата запроса от узла и передача его пользователю
1. Таймаут не произошёл и узел вернул ответ: код 200 или 429
2. Распределитель перенаправляет полученный код соответствующему пользователю без изменений

### Сценарий 23. Возврат узла в список, после его восстановления
1. Распределитель получает сообщение о том, что узел поднялся 
2. Распределитель добавляет узел в список живых узлов

### Сценарий 24. Получение и передача административного запроса
1. Распределитель получает запрос, содержащий поле admin_id
2. Распределитель выбирает следующий живой узел по принципу из сценария 1.1.
3. Распределитель отправляет запрос на этот узел
4. В случае, если распределитель не получает ответ от узла до истечения таймаута, распределитель возвращает `503 Service unavaliable`
