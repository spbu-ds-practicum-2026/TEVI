# Техническое решение проекта «Middleware»

## Введение
- **Бизнес-задача:**
	Целевой сервис (API-шлюз) принимает поток запросов от пользователей. При резком скачке трафика - например, из-за всплеска активности или DDoS-атаки - одиночный сервер не справляется с нагрузкой: растет задержка ответа, вплоть до отказа обслуживания
	Для защиты сервиса перед ним ставится слой фильтрации трафика (rate limiting middleware), ограничивающий число запросов от каждого пользователя за единицу времени. На одном узле этот слой сам становится узким местом (bottleneck) и единой точкой отказа (single point of failure): при его отказе весь трафик уходит на сервис без ограничений, либо сервис становится недоступен

- **Идея решения:**
	Создать распределенный слой фильтрации (_middleware_), состоящий из нескольких независимых узлов, каждый из которых принимает запросы и локально ведет счетчик запросов по пользователям. Узлы обмениваются состоянием, чтобы совместно следить за глобальным лимитом пользователя, и не имеют общей точки отказа.   

- **Краткое описание:**
	Distributed rate limiting middleware - учебный проект, реализующий прототип промежуточного слоя фильтрации запросов, который стоит перед целевым сервисом, ограничивает трафик и сохраняет работоспособность системы при отказе части узлов

	Проект является распределённой системой, потому что:
	- состоит из нескольких независимых узлов, каждый со своей локальной памятью
	- узлы не имеют общей памяти и общаются сообщениями
	- состояние лимитов согласуется между узлами асинхронно
	- система сохраняет работоспособность при отказе отдельных узлов

- **Цель проекта:**  
	Реализовать прототип распределённого middleware, который:
	- ограничивает число запросов от каждого пользователя за единицу времени
	- сохраняет доступность при отказе отдельных узлов и сетевых разделениях
	- обеспечивает сходимость состояния лимитов между узлами за конечное время

- **Задачи:**
	- спроектировать архитектуру распределённого middleware
	- реализовать приём и обработку входящего трафика на узле middleware
	- реализовать локальный учёт запросов по пользователям
	- реализовать обмен состоянием между узлами
	- реализовать детектор отказа узлов (failure detector)
	- реализовать обработку сетевых разделений и восстановление после слияния
	- реализовать тестирование и chaos-сценарии

- **Основания для разработки:**  
	учебный проект по курсу «Основы распределённых вычислений» в СПбГУ

## Глоссарий
| Термин                                        | Определение                                                                                                           |
| --------------------------------------------- | --------------------------------------------------------------------------------------------------------------------- |
| Целевой сервис                                | Сервис (API-шлюз), перед которым ставится middleware и который обрабатывает запросы, пропущенные middleware           |
| API-шлюз                                      | Единая точка входа для запросов пользователей                                                                         |
| Запрос                                        | Обращение пользователя к системе с целью выполнения операции                                                          |
| Поток запросов                                | Совокупность запросов, поступающих в систему за промежуток времени                                                    |
| Пользователь                                  | Клиент системы, который отправляет запросы в систему и получает ответы от нее                                         |
| Трафик                                        | Количество запросов от пользователей в единицу времени, измерение: RPS (Requests Per Second)                          |
| Всплеск активности                            | Кратковременное резкое увеличение количества запросов от пользователя или группы пользователей                        |
| DDoS-атака                                    | Распределённая атака, при которой большое число источников одновременно отправляет запросы с целью перегрузки сервиса |
| Слой фильтрации (middleware)                  | Промежуточный слой между пользователем и целевым сервисом, который перехватывает запросы и выполняет их фильтрацию    |
| Счетчик запросов                              | Структура данных, которая хранит число запросов пользователя за текущий промежуток времени                            |
| Лимит                                         | Максимальное число запросов, которые может отправить пользователь за единицу времени                                  |
| Локальный лимит                               | Лимит, который хранится и обрабатывается конкретным узлом                                                             |
| Глобальный лимит                              | Общий лимит пользователя, согласованный между всеми узлами кластера                                                   |
| Узкое место (bottleneck)                      | Компонент системы, который ограничивает её общую производительность                                                   |
| Единая точка отказа (Single Point of Failure) | Компонент, отказ которого приводит к отказу всей системы                                                              |
| Узел                                          | Самостоятельный экземпляр middleware, который обрабатывает запросы независимо от других узлов                         |
| Кластер                                       | Множество узлов middleware, которые знают друг о друге и обмениваются состоянием                                      |
| Локальная память узла                         | Память, доступная только данному узлу; хранит его счётчики и состояние                                                |
| Общая память узлов                            | Разделяемая память, доступная всем узлам; в проекте отсутствует (узлы общаются сообщениями)                           |
| Состояние узла                                | Совокупность счётчиков запросов и метаданных, которыми узел обладает в данный момент                                  |
| Сходимость состояния узлов                    | Свойство, при котором состояния всех узлов приходят к согласованному виду за конечное время                           |
| Сообщение                                     | Единица данных, передаваемая между узлами по сети                                                                     |
| Отказ узла                                    | Прекращение обработки запросов узлом вследствие сбоя или сетевой недоступности                                        |
| Детектор отказа узла (failure detector)       | Механизм, определяющий, доступен ли узел, на основе периодических проверок                                            |
| Восстановление узла                           | Возвращение узла в рабочее состояние и синхронизация его состояния с кластером                                        |
| Слияние узлов                                 | Объединение состояний узлов после восстановления связи между ними                                                     |
| Сетевое разделение                            | Ситуация, при которой связь между узлами нарушена и кластер распадается на изолированные группы                       |
| Chaos-сценарии                                | Тесты, моделирующие отказы и аномалии (отказ узла, задержка, разделение сети) для проверки устойчивости системы       |

## Функциональные требования
Система должна предоставлять следующие функции:
	- Приём запросов от пользователей.
	- Ограничение числа запросов от одного пользователя за единицу времени.
	- Пропуск запроса к целевому сервису с ответом `200 OK`, если лимит не превышен.
	- Отклонение запроса с ответом `429 Too Many Requests`, если лимит превышен.
	- Сохранение работоспособности при отказе части узлов.

---

## Ограничения на предметную область
- Система развёртывается на одной машине через `docker compose`.
- Целевой сервис — заглушка, возвращающая `200 OK`.
- Аутентификация не реализуется: `user_id` передаётся в запросе.
- Конфигурация лимитов: лимит задается статически при старте узлов (динамическое изменение лимитов «на лету» не реализуется).
- Система ограничивает по `user_id`, а не защищает от DDoS

---

## Нефункциональные требования
- Масштабируемость: пропускная способность системы растёт при добавлении новых узлов в кластер. Новый узел подключается без изменения кода и конфигурации остальных узлов.
- Конечная согласованность: при отсутствии новых запросов состояния узлов сходятся за конечное время.
- Поведение при сетевых аномалиях: при сетевых разделениях доступность сохраняется в ущерб строгой согласованности; возможны кратковременные превышения лимитов.
- Доступность: при отказе меньшинства узлов кластера система продолжает принимать и обрабатывать запросы.
- Отказоустойчивость: отказ отдельного узла не приводит к потере ранее синхронизированных данных о запросах. Данные, не успевшие синхронизироваться, могут быть утеряны — это осознанный компромисс в пользу доступности.
- Надёжность обмена: сообщения между узлами могут доставляться повторно; повторная доставка не приводит к двойному учёту в счётчике запросов.
- Обнаружение отказов: система автоматически обнаруживает отказавший узел и исключает его из обработки запросов и обмена состоянием.
- Восстановление: вернувшийся в кластер узел автоматически синхронизирует состояние счётчиков без участия оператора.
- Производительность: система сохраняет низкую задержку обработки запросов при высокой входящей нагрузке.

## Пользовательские сценарии
### Отправка запроса в пределах лимита
1. Пользователь отправляет запрос к сервису.
2. Система проверяет число запросов пользователя за текущее временное окно.
3. Если лимит не превышен, система пропускает запрос к сервису.
4. Пользователь получает ответ сервиса со статусом `200 OK`.
### Превышение лимита запросов
1. Пользователь отправляет $N$ (максимальное разрешенное количество) запросов за временное окно.
2. Система пропускает все $N$ запросов, пользователь получает `200 OK` на каждый.
3. Пользователь отправляет $N+1$-й запрос в то же временное окно.
4. Система проверяет число запросов и определяет, что лимит исчерпан.
5. Система отклоняет запрос, сервис его не получает.
6. Пользователь получает `429 Too Many Requests`.
### Сброс лимитов для пользователя
1. Пользователь исчерпал лимит и получает `429 Too Many Requests`.
2. Пользователь ждёт сброса лимита и отправляет запрос.
3. Система считает запрос новым, так как лимит возобновился.
4. Система пропускает запрос к сервису.
5. Пользователь получает `200 OK`.
