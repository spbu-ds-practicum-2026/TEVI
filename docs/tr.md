# Техническое решение проекта «Middleware»

## Введение
- **Бизнес-задача:**
	Целевой сервис (API-шлюз) принимает поток запросов от пользователей. При резком скачке трафика - например, из-за всплеска активности или DDoS-атаки - одиночный сервер не справляется с нагрузкой: растет задержка ответа, вплоть до отказа обслуживания.
	Для защиты сервиса перед ним ставится слой фильтрации трафика (rate limiting middleware), ограничивающий число запросов от каждого пользователя за единицу времени. На одном узле этот слой сам становится узким местом (bottleneck) и единой точкой отказа (single point of failure): при его отказе весь трафик уходит на сервис без ограничений, либо сервис становится недоступен.

- **Идея решения:**
	Создать распределенный слой фильтрации (middleware), состоящий из нескольких независимых узлов, каждый из которых принимает запросы и локально ведет счетчик запросов по пользователям. Узлы обмениваются состоянием, чтобы совместно следить за глобальным лимитом пользователя, и не имеют единственного центрального узла обработки.

- **Краткое описание:**
	Distributed rate limiting middleware - учебный проект, реализующий прототип промежуточного слоя фильтрации запросов, который стоит перед целевым сервисом, ограничивает трафик и сохраняет работоспособность системы при отказе части узлов.

	Проект является распределённой системой, потому что:
	- состоит из нескольких независимых узлов, каждый со своей локальной памятью
	- узлы не имеют общей памяти и общаются сообщениями
	- состояние лимитов согласуется между узлами асинхронно
	- система сохраняет работоспособность при отказе отдельных узлов

- **Цель проекта:**  
	Реализовать прототип распределённого middleware, который:
	- ограничивает число запросов от каждого пользователя за единицу времени
	- сохраняет доступность при отказе отдельных узлов и сетевых разделениях
	- обеспечивает сходимость состояния лимитов между узлами за конечное время

- **Задачи:**
	- спроектировать архитектуру распределённого middleware
	- реализовать приём и обработку входящего трафика на узле middleware
	- реализовать локальный учёт запросов по пользователям
	- реализовать обмен состоянием между узлами
	- реализовать детектор отказа узлов (failure detector)
	- реализовать обработку сетевых разделений и восстановление после слияния
	- реализовать тестирование и chaos-сценарии

- **Основания для разработки:**  
	учебный проект по курсу «Основы распределённых вычислений» в СПбГУ.

## Функциональные требования
Система должна предоставлять следующие функции:
- Приём запросов от пользователей.
- Ограничение числа запросов от одного пользователя в рамках скользящего окна времени.
- Пропуск запроса к целевому сервису с ответом `200 OK`, если лимит не превышен.
- Отклонение запроса с ответом `429 Too Many Requests`, если лимит превышен.

### Ограничения на предметную область
- Система развёртывается на одной машине через `docker compose`.
- Целевой сервис — заглушка, возвращающая `200 OK`.
- Аутентификация не реализуется: `user_id` передаётся в запросе.
- Размер скользящего окна $T$ и лимит $N$ одинаковы для всех узлов кластера. В примерах и сценариях используются $T = 60$ секунд и $N = 10$ запросов; прототип допускает иные значения, задаваемые в конфигурации.
- Система ограничивает по `user_id`, а не защищает от DDoS.

## Нефункциональные требования
- Гарантия лимита: Система стремится соблюдать глобальный лимит $N$ для каждого `user_id` суммарно по всем узлам кластера. При асинхронной синхронизации возможно временное превышение; после сходимости решения принимаются по объединённым счётчикам. Количественная граница в прототипе не фиксируется.
- Масштабируемость: Пропускная способность растёт при добавлении узлов кластера без изменения кода и конфигурации остальных узлов.
- Поведение при сетевых аномалиях (AP-система): При сетевых разделениях доступность ставится выше строгой согласованности. Каждая изолированная группа узлов продолжает независимо принимать трафик.
- Конечная согласованность: При восстановленной связи, продолжающейся доставке сообщений и отсутствии новых запросов счётчики узлов по каждому `user_id` сходятся за конечное время. При сдвиге скользящего окна запросы, вышедшие за пределы последних $T$ секунд, исключаются из подсчёта.
- Отказоустойчивость: При отказе отдельного узла остальные узлы продолжают обрабатывать запросы. Ранее синхронизированные данные сохраняются; несинхронизированные могут быть потеряны.
- Надёжность обмена: Доставка сообщений At-least-once. Слияние счётчиков идемпотентно — повторная доставка не приводит к двойному учёту запросов.
- Обнаружение отказов и восстановление: Система обнаруживает недоступность узла и исключает его из обмена состоянием. Вернувшийся в кластер узел автоматически синхронизирует счётчики без участия оператора.

## Пользовательские сценарии
**Правила работы лимита:**
Ограничение действует для конкретного `user_id` суммарно по всем узлам кластера на протяжении скользящего временного окна длительностью $T$ (например, 60 секунд).

Отклонённые системой запросы (получившие ответ `429`) не учитываются в счётчике и не расходуют лимит. Такое поведение выбрано потому, что главная цель middleware — ограничить реальную нагрузку на целевой сервис, а не наказывать пользователя за повторные попытки.

### Отправка запроса в пределах лимита
1. Пользователь отправляет запрос через любой узел middleware.
2. Узел проверяет сумму запросов пользователя за окно.
3. Если лимит не превышен, запрос пропускается к сервису.
4. Пользователь получает ответ сервиса со статусом `200 OK`.

### Превышение лимита запросов
1. Пользователь отправляет $N+1$-й запрос за окно.
2. Узел определяет, что лимит исчерпан.
3. Запрос отклоняется.
4. Пользователь получает `429 Too Many Requests`.

### Восстановление лимита
1. Пользователь ждёт, пока часть запросов выйдет за границу окна.
2. Сумма запросов за окно становится меньше $N$.
3. Следующий запрос пропускается к сервису.
4. Пользователь получает `200 OK`.

### Сетевое разделение и восстановление
1. Установлен лимит: 10 запросов на окно.
2. Узел A принимает 8 запросов, узел B принимает 8 запросов, связь между ними нарушена. Оба пропускают локально.
3. Связь восстанавливается, узлы синхронизируются.
4. Оба узла учитывают 16 запросов за окно.
5. Следующий запрос отклоняется как `429`.
6. После выхода старых запросов за границу окна лимит восстанавливается.
